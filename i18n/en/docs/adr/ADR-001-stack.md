# ADR-001 — Project stack

- **Date:** 2026-11-14 (pre-event proposal)
- **Status:** **proposal**; updated on Nov 14 with the EDA data (see «Update Nov 14, 2026, afternoon»). **Pending signature by C (Mauricio).**
- **Decides:** C (Mauricio); pending signature

## Context

A public web tool has to be built in ~24 hours, with six people who program and their
agents. The data are in the IRSA/IPAC archive and the libraries that know how to read them
(`astropy`, `pyvo`, `astroquery`) exist **only in Python**. The statement explicitly suggests
Astropy and Aladin.

Constraints:

- 24 hours and a fixed submission deadline.
- Six people in parallel: the work has to be separable.
- A public URL that the jury can open has to remain.
- No infrastructure budget or usable GPU for anything heavy.

## Options considered

| Option | Pros | Cons | Cost |
|---|---|---|---|
| **Python/FastAPI + React/Vite + Aladin Lite** | Separates backend and frontend, two people in parallel from hour 1; looks like a public tool; Aladin solves the sky | Two deployments, CORS, a contract to maintain | Medium |
| Streamlit | All in Python, comes up in minutes | Hard to polish; does not look like a public tool; a smooth blink is costly | Low |
| Static front + Aladin Lite, no backend | Trivial deployment, nothing to maintain | **Depends on IRSA responding with CORS** (ruled out on Nov 14: IRSA gives no CORS outside HiPS, `docs/09`); cannot crop, normalize or subtract on the server side | Low, but with a risk we don't control |

## Update Nov 14, 2026, afternoon — deployment decision (C, with the EDA data)

**Status: proposal by C (Mauricio), pending the team's go-ahead at the next standup.**

### Data that decide (EDA, `eda/resultados/latencia_cutouts.json`, `docs/09_EDA_HALLAZGOS.md`)

- A 0.1° cutout takes **7.3 s median, 10.8 s p90, 29 s maximum** (~3.9 MB), with **503s at times**.
- 25 cutouts with 4 threads: **52 s** wall time. A complete «live» blink does not fit in a reasonable wait.
- **IRSA does not respond with CORS** (neither SIA2 nor files): everything other than the HiPS cube goes through a backend.
- SIA2 to `spherex_dr1` and `spherex_qr3`: 1–3.5 s each; header via HTTP Range ~35 KB, ~0.1 s effective.

### Decision

| Piece | Where it runs | Why |
|---|---|---|
| Frontend | **Vercel** (project `spherex-planet-x`, eMind team, Hobby), production from `main` | Already works; the organizers specified it |
| **The 5 test fields** (the demo) | **Precomputed as statics** in `scaffold/frontend/public/precalc/<id>/` (JSON in the shape of the contract + PNG), generated by D1's script and versioned | The demo **never** waits for IRSA nor depends on wifi. It is also the offline mode |
| `/api/resolve`, `/api/epochs` | **Vercel Python Functions** in the same project (`api/`) | 1–3.5 s: they fit easily. Same domain, no CORS |
| `/api/frames` for arbitrary coordinates | **Vercel Python Functions, with a time budget**: downloads in parallel (4) as much as it can, returns what is ready and `pending` with the rest; the frontend asks again and shows frames as they arrive | Avoids the 52 s wait without setting up another service |
| Plan B if the functions are not enough (maximum time, astropy/reproject memory, package size) | **The same FastAPI in a container** (Render or Fly, free tier) behind `/api` with a Vercel *rewrite* | Changing place does not change the contract |

Rules that follow from this:

- **Cache:** the functions have no persistent disk (only `/tmp` per instance). Nothing is designed that
  depends on the cache for the demo: that is what the precomputed data are for.
- **Maximum function time:** set with `maxDuration` in `vercel.json`. Before relying on a value,
  **check the current maximum of the Hobby plan in the Vercel documentation** (D1, at the first deployment of `api/`).
- **Demo objects:** the five test objects must work. WISE 0855 is a mandatory case and is
  always shown, saying that in a single exposure it looks faint (its motion is seen with the subtraction and, when it
  exists, with D2's per-sweep sum, pending, and V2's CatWISE2020 overlay, done on the `v/v2-catwise` branch and PR pending). eps Ind B is where the
  motion is seen most clearly; Barnard is seen but saturates. Always center on the **propagated position**, not the J2000 one.
- **Deployments:** Vercel Hobby only builds Mauricio's commits; production comes from his merges.
  See README §2.

### What each person does with this

- **D1 (Vladimir):** precompute script for the 5 fields → `public/precalc/`; `api/` with `resolve` and `epochs`.
- **D2 (Bryan):** `frames` with a time budget and partial response (`pending`).
- **V1 (Antonia):** the blink reads `precalc/<id>/` first if the field is a test one; if not, `/api/frames` with
  retry and frames that appear as they arrive.
- **C (Mauricio):** measure the first deployment of `api/` and activate plan B if it is not enough.

## Decision

**Python 3.11 + FastAPI on the backend; React + Vite + TypeScript with Aladin Lite 3.8.2 on the frontend.**
Disk cache. Frontend on Vercel (decided Nov 14). The backend for arbitrary coordinates: C's proposal from the update above (Vercel Python Functions with a time budget; plan B, the same FastAPI in a container), with the measured cutout time: median 7.3 s, p90 10.8 s, max. 29 s, ~3.9 MB regardless of size, 503s at times (`docs/09` §6). The 5 test fields are served precomputed as statics.

The API contract, which is what allows working in parallel, is in
[`../03_ARQUITECTURA.md`](../03_ARQUITECTURA.md).

## Consequences

**Easy:** D and V working at the same time without stepping on each other from the first hour; using the whole
Astropy ecosystem; caching and normalizing on the server side, which is what makes the blink viable.

**Hard:** a contract and two deployments have to be maintained; CORS between frontend and backend has to be
configured correctly once.

**If we are wrong:** Path A (Aladin Lite loading the DR1 HiPS cube directly) **does not depend on the
backend**. If the backend goes down or doesn't arrive in time, that part keeps working and there is something to
show. That is the safety net of this decision.
