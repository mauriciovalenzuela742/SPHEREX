# 04 — 方法论：四个人、四个智能体、24 小时

四人团队配合智能体的主要风险不是没有想法：而是**互相踩踏**。
四个智能体在同一个仓库上飞快写入，会产生冲突、重复代码，以及凌晨三点崩掉的 `main` 分支。本文档是为了避免这种情况而达成的约定。

---

## 角色

四个角色，每个角色是一批文件的负责人。（在这个六人团队中，D 拆分为 D1 访问和 D2
帧，V 拆分为 V1 blink 和 V2 天空；见 [`README.md`](../README.md) §3。）**负责人**的意思是：这个人决定，其他人提请求。并不意味着他独自工作。

### D — 数据（后端 / IRSA）
负责 `scaffold/backend/app/irsa/`、`scaffold/backend/app/cache/`。
查询 SIA2、下载 cutouts、读取 MEF、按波段分组、解析 WCS 和波长。
它是关键路径：**如果这里不行，就没有项目。**
合适的人选：对科学 Python 和观测天文最熟练的人。

### V — 查看器（前端）
负责 `scaffold/frontend/src/`。
Aladin Lite、blink 面板、控件（拉伸、颜色、fps）、可查询的 URL。
合适的人选：对现代 Web 最熟练的人。

### C — 科学与验证
负责 `data/campos_de_prueba.yml`、`tests/`、`docs/`。
核实显示的内容是否正确：裁切图是否来自它所声称的天区，天体是否在
Gaia 预测的位置，光谱是不是伪影。**他有权说
“这不对”，而不必提出修复方案。**
合适的人选：天文判断力最强的人。在这个团队中，自然是物理这边的人。

### N — 叙事与交付
负责 `README.md`、演示、pitch 和提交表单。
**从第 0 小时**就开始工作，而不是最后。黑客松的经典错误是把
交付留到最后两个小时，然后发现表单缺了一半。
合适的人选：公开演讲最好的人，因为他同时也是演讲者。

> **角色不是牢笼。** 从第 12 小时起，当关键路径疏通后，D 和
> V 分担额外的要点。但 C 和 N **不会解散**：如果没有人验证、没有人准备
> 交付，项目就会迟交并带着错误。

## 代码如何协调

**基于主干的短分支。** `main` 始终能启动。

```bash
git switch -c d/sia2-epochs      # inicial del rol + tema
# ... trabajo ...
git push -u origin d/sia2-epochs
# PR. Lo mira otro. Se mergea.
```

规则：

1. **没有人直接推送到 `main`。** 你不行，你的智能体也不行。
2. **分支存活不超过 3 小时。** 如果一个分支超过了，说明任务太大。
3. **PR 由一个人审查，而不是智能体。** 看 diff 只需两分钟，却能省下数小时。
4. **API 契约要先在 `docs/03_ARQUITECTURA.md` 中修改**并通知，然后才动代码。悄悄改契约会在对方不知情的情况下把他卡住。
5. **仓库中不放任何 FITS。** `data/cache/` 在 `.gitignore` 中。

### Worktrees：每人一个文件夹

如果两个人（或两个智能体）在同一个文件夹里工作，他们会不声不响地互相覆盖。用
`git worktree`，每个人在同一个仓库上都有自己的副本：

```bash
git worktree add ../spherex-d d/sia2-epochs
cd ../spherex-d
```

这就是四个智能体协作与四个智能体争抢同样文件的区别。

## 90 分钟周期

黑客松被划分为 90 分钟的区块。在每个区块结束时，**所有人站着开五分钟会**，
使用命令 `/standup`：

1. **什么东西已经能用了** — 不是“我做了什么”，而是什么可以打开来看。
2. **什么被卡住了，被谁卡住。**
3. **接下来 90 分钟我做什么。**

五分钟。不看屏幕。如果有人需要更多时间，另外再谈。

为什么是 90：足够完成一件事，又短到走错路也不至于耗掉半夜。

## 在这里如何使用智能体

这是区分“使用智能体的团队”和“被智能体赢了的团队”的地方。

**一个会话负责一条战线。** 不要在同一个 Claude Code 会话里混合数据后端和前端。上下文会被污染，智能体开始犯低级错误。如果换了主题，就开新会话，需要带上上下文时用 `/traspaso`。

**智能体提议，人决定。** 凡是涉及超过两个文件的事情：先出计划，再批准。在黑客松里放任它跑的诱惑极大，而这是最快落得“凌晨 5 点面对 2,000 行没人看得懂的代码”的方式。

**验证产物，而不是报告。** 智能体说“已经能用了”是一个数据点，不是事实。
打开 URL。看图像。数历元。这不是不信任：而是智能体看不到屏幕。

**某件事试到第三次还不行，就换思路，而不是换提示词。** 如果你已经三次在纠正同一件事，问题不在于你怎么向它提要求。

**绝不让智能体自己决定范围。** 范围由团队依据
[`05_PLAN_24H.md`](05_PLAN_24H.md) 的计划来定。如果放任不管，智能体会把挑战的所有要点都做一半，而不是完整做好三个。

**把会弄乱上下文的事交给子智能体。** 在 IRSA 文档中搜索、尝试
20 个 SIA2 查询、审查 UI：这些交给 `explorador-datos`、`revisor-cientifico` 或
`revisor-interfaz`，它们返回结论而没有冗余。

## Claude Code 与 Antigravity 之间的分工

如果团队中同时使用这两种工具，默认的分工是**按文件**，绝不按主题：

| 工具 | 文件 |
|---|---|
| Claude Code | `backend/`、`tests/`、`docs/` |
| Antigravity | `frontend/` |

两个智能体编辑同一个文件会不声不响地互相覆盖，而且两边都不会告诉你。

## “完成”的定义

一项任务完成，当：

- [ ] 它在 `data/campos_de_prueba.yml` 中**至少一个真实天区**上能工作。
- [ ] 另一个人打开并看到它能工作。
- [ ] 没有覆盖到的部分已经大声说出（缺失的波段、未测试的情形）。
- [ ] 没有破坏任何已经能用的东西（`/chequeo-demo`）。

不能因为某个智能体说完成了，就算完成。

## 三个强制停靠点

它们是唯一不可协商的事，无论代码发生什么：

| 时刻 | 发生什么 |
|---|---|
| **T − 6 h** | **范围冻结。** 不再开始任何新事物。只修复和打磨已有的 |
| **T − 4 h** | **录好演示。** 即使应用仍在改进，视频也必须就绪。如果之后有改进，就重录。如果来不及，视频已经在那儿了 |
| **T − 2 h** | **提交已上传。** 表单填完整，链接放好，AI 使用声明写好。如果还有时间，可以编辑；但**已经提交了** |

`T` 是本地赛事提交截止的时间。在圣地亚哥的赛事中，JP 于 11 月 14 日确认
（由组织方现场通知）是在**周日 15 日 11:00**（[`08_REGLAS_DEL_EVENTO.md`](08_REGLAS_DEL_EVENTO.md)）。
这个数字决定了其他一切的顺序。

获胜的项目不是代码最多的那个，而是完整交付的那个。
