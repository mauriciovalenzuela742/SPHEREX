# 音频 2/2 — SPHEREx：策略、团队与路演

这是为 Juan Pablo 准备的材料，用于前往 NASA Space Apps Challenge 2026。他所在天文实验室的六人团队将接下挑战 **Planet X and SPHEREx**。

这是两段音频中的第二段。第一段讲挑战要求什么、使用哪些数据。
这一段讲的是**如何组织、先做什么、评审团奖励什么，以及如何展示**。

核心思想：在黑客松中，获胜的项目几乎从来不是代码最多的那个，而是完整交付的那个。

---

## 1. 隐藏的评分标准：题面中的八条建议

挑战中有一节“潜在考量”，列出八个要点，并说你“可以但不必”考虑。实际上**它们就是评分标准**：它们是挑战作者期望用来区分优秀项目的依据，也是 NASA 评委会认可的东西。

这八条是：工具要便于在新数据到来时更新；以有创意的方式展示全部 102 个红外波段，若能即时生成光谱则明确加分；允许对不同历元拍摄的图像做加法或减法；让用户选择视场；允许叠加其他望远镜（如 Gaia 或 WISE）的数据；**可以通过在 URL 中带上坐标来查询工具**，以便嵌入其他网站；显示元数据，例如污染标志；以及使用已有的公共工具，并明确点名 Astropy 和 Aladin。

有意思的是：**八条中有七条成本低或极低。** 唯一真正昂贵的是 102 个波段这一条，而它恰恰是差异化所在。所以八条都要完成，并且有一个先后顺序。

---

## 2. 架构：两条路径，两条都要有

项目有一条快速路径和一条完整路径，关键在于**快速路径是真实存在的**。

**路径 A** 是 Aladin Lite 直接加载 Data Release 1 的全天空立方体，该立方体以 HiPS 格式发布。用户浏览天空并拖动波长滑块。零后端。它提供 102 个波段、全天空背景以及星表叠加层。它不提供时间轴，因为这个立方体是合成的马赛克，而不是一系列历元。成本：数小时，而不是数天。技术风险低。

**路径 B** 是带后端的时间闪烁（blink）。服务器按位置查询档案库，请求每个历元的裁切图，按波段分组、归一化，并返回按时间排序的序列。这才是挑战本身，也是工作的主体。它的瓶颈是裁切图的延迟：没有缓存，演示就撑不下来。

**两条路径放在同一个屏幕上**，并排显示：Aladin 提供背景和波长，旁边的面板提供时间闪烁。用户立刻就能明白这是同一份数据的两个轴。

路径 A 也是项目的保险：如果后端来不及完成，仍然有真实的东西可以展示。

已决定的技术栈：后端用 Python 加 FastAPI，因为能读取这些数据的库只存在于 Python；前端用 React 加 Vite 和 Aladin Lite；磁盘缓存；前端部署在 Vercel，后端待定（Vercel Functions 或容器，取决于一张裁切图的实测耗时）。

一个能省很多工作的设计决策：**后端返回已经渲染好的 PNG 图像，而不是 FITS 文件。** 把 FITS 发给浏览器，就得用 JavaScript 写一个 FITS 读取器，并手动做拉伸和色彩映射：工作量翻倍，错误翻三倍。代价是改变拉伸需要回到服务器，而有了缓存这很便宜。

还有一个看似次要、其实不然的细节：**一个序列中的所有帧都用相同的上下限归一化。** 如果每一帧各自拉伸，整体就会闪烁，分不清真实运动和尺度变化。

## 3. 首先要确定的：API 契约

这是让六个人从第一个小时起就能并行推进的东西。

在第一个小时写出契约：有哪些端点、接受哪些参数、确切返回什么。在后端还不存在时，前端针对一个返回同样形状数据的模拟器工作。没有人等任何人。

支撑它的规则是：**如果有人要改契约，先在文档里改**，通知团队，然后才动代码。悄悄改契约会在对方不知情的情况下把他卡住，而这在凌晨三点会耗掉数小时。

契约中有两个字段值得一提。其一：每一帧都返回**它的波长**，这不是可选项：它能避免线性可变滤光片的问题，并且在屏幕上展示出来，向评审团证明团队理解这台仪器。其二：警告以列表形式传递，而不是作为错误。波段总是会缺失；如果这会让请求失败，工具就无法使用。

## 4. 六个人、他们的智能体，以及真正的风险

六人团队配合 AI 助手的主要风险不是没有想法，而是**互相踩踏**。多个智能体在同一个仓库上飞快写入，会产生冲突、重复代码，以及凌晨崩掉的主分支。

建议的分工是四个角色，每个角色是一批文件的负责人。负责人的意思是由这个人决定、其他人提请求；并不意味着他独自工作。

**数据**：查询档案库、下载裁切图、读取 FITS、按波段分组、解析坐标和波长。这是关键路径：如果这里不行，就没有项目。

**查看器**：Aladin Lite、闪烁面板、控件、可查询的 URL。

**科学与验证**：核实显示的内容是否正确。裁切图是否来自它所声称的天区，目标是否在 Gaia 预测的位置，光谱是不是伪影。**他有明确的权限可以说“这不对”，而不必提出修复方案。**

**叙事与交付**：README、演示、路演和表单。他从第零小时就开始工作，而不是最后才开始。黑客松的经典错误是把交付留到最后两个小时，然后发现表单缺了一半。

从第十二小时起，当关键路径疏通后，数据和查看器分担额外的要点。但科学和叙事不会解散：如果没有人验证、没有人准备交付，项目就会迟交并带着错误。

关于代码：分支存活不超过三小时，没有人直接推送到主分支，每次变更由一个人（而不是智能体）审查，因为看一个 diff 只需两分钟，却能省下数小时。还有 worktree：每人一个文件夹，因为两个智能体在同一个文件夹上会不声不响地互相覆盖，而且两边都不会告诉你。

## 5. 如何使用智能体而不被智能体“赢”

这是区分“使用智能体的团队”和“被智能体赢了的团队”的地方。共有五个习惯。

**一个会话负责一条战线。** 不要在同一个会话里混合数据后端和前端：上下文会被污染，助手开始犯低级错误。

**智能体提议，人决定。** 凡是涉及超过两个文件的事情：先出计划，再批准。在黑客松里放任它跑的诱惑极大，而这是最快落得“凌晨五点面对两千行没人看得懂的代码”的方式。

**验证产物，而不是报告。** 智能体说“已经能用了”是一个数据点，不是事实。要打开 URL、看图像、数历元。这不是不信任：而是智能体看不到屏幕。

**某件事试到第三次还不行，就换思路，而不是换提示词。** 如果你已经三次在纠正同一件事，问题不在于你怎么向它提要求。

还有，**绝不让智能体自己决定范围。** 如果放任不管，智能体会把挑战的八个要点都做一半，而不是完整做好三个。

## 6. 分块计划，以及切断点在哪里

节奏是九十分钟一个区块，每个区块结束时，站着开五分钟会，不看屏幕，每个人说三件事：什么东西已经能用了——不是做了什么，而是什么可以打开来看——什么被卡住了、被谁卡住，以及接下来九十分钟要做什么。

九十分钟足够完成一件事，又短到走错路也不至于耗掉半夜。

**第零小时用来对齐。** 一起大声读题面、分配角色、确认提交截止的准确时间，并在六台电脑上把骨架跑起来。如果骨架跑不起来，在它跑起来之前没有人继续前进。

**第一到第三小时是数据的“真相时刻”。** 真实查询、每个天区有多少个历元、计时测量一张裁切图要多久，以及当天最重要的问题：同一天区的两个历元之间波长变化了多少。如果裁切图因为太慢而不可行，**计划就在这里改变，而不是在第十五小时。**

**到第八小时为止，是关键路径**，里程碑非常具体：*手工输入一个坐标，屏幕上就出一段小视频。* 丑、慢、只有一个波段都无所谓。如果到第八小时还没有小视频，其他一切暂停，六个人都投入这件事。

**第八到第十四小时，把它做好**，按价值排序：波段选择器，然后是控件，然后是图像相减，然后是名称解析，然后是可分享的 URL，然后是 Gaia 叠加层，然后是标志（flags），只有在前面所有事情都收尾之后，才做即时光谱。

然后是**三个强制停靠点**，这是唯一不可协商的东西。

距截止六小时：**范围冻结**。不再开始任何新事物。没开始的就不开始，已开始的要么做完要么移除，因为**做了一半的功能会扣分**：评委偏偏就点在那里。

距截止四小时：**录好演示**，即使应用还在改进。如果之后有改进，就重录。如果来不及，视频已经在那儿了。

距截止两小时：**已提交**。表单填完整，链接放好，AI 使用声明写好。之后还可以继续编辑，但已经提交了。

## 7. 可能出什么问题

已识别十个风险；值得记住前四个。

**档案库的裁切图太慢。** 这是一切所依赖的假设。第三小时就能定论。如果确实慢，B 计划是激进缓存、预热，并在帧到达时逐帧显示；C 计划是基于一组约十个预先计算好的精选天区运行，并且毫不掩饰地说出来：今天我们提供这些天区，架构可以扩展。

**由于线性可变滤光片，各历元不可比。** 这是最微妙的风险，也是最可能毁掉结果而没人明白原因的风险。它出现时警报信号很明显：第一次闪烁看起来像频闪灯。

**Wi-Fi 断了。** 概率高：几乎每次黑客松都会发生。B 计划是强制性的，不是可选的：一个降级模式，从缓存提供五个天区，不碰网络；演示视频要下载到演讲者电脑的硬盘上，而不是放在云端。

**项目迟交或不完整。** 这是好项目一无所获的头号原因，而且没有 B 计划。所以才有那三个停靠点。

还有一条最好事先写下来，免得凌晨四点再重新争论：**不训练任何模型。** 没有时间，没有标签，也没有必要。

## 8. 为什么不用视频模型，被问到时怎么答

要把这点想清楚，因为总会有人问，不论团队内外。

视频理解架构——TimeSformer、ViViT、VideoMAE、X-CLIP——是用来理解自然视频的模型。它们是用人、物体和动作预训练的。天文序列的统计特性——几乎空白的背景、点状源、伪影、几个像素的位移——与之完全不同，所以预训练（这是它们的全部价值）无法很好地迁移。此外没有标签，而这个情形用利用问题物理特性的经典方法已经解决得很好：静态背景上的线性轨迹。

这里自动检测的最新技术是 **shift-and-stack**：按候选速度平移每张图像再叠加，使移动的物体相干相加而噪声不会。参考实现 KBMOD 在 GPU 上运行，每分钟探索约一百亿条候选轨迹；借助它，DEEP 巡天识别出 105 个新的海外天体。这很昂贵，24 小时内做不了。把它作为未来工作提出，比硬去尝试更诚实。

**而这里是团队自己的优势。** Francisco Förster 的实验室构建了 ALeRCE，这个智利的 broker 处理 ZTF 的警报流，并为 LSST 做准备。它的图像块分类器是一个卷积网络，作用于首次探测的科学图像、参考图像和差异图像裁切图，并被设计为利用旋转不变性。这——一个作用于裁切图、不变性由人手工选定的小网络——**才是这个问题正确的人工智能模型**，而不是视频 transformer。

但真正的差异化贡献甚至不是把那个分类器放进查看器，而是**实时分类的规范**：阈值、假阳性、如何向用户呈现一个可疑候选、如何收集这个人给出的标签。把这套规范应用到界面上，是黑客松里其他团队都不会有的东西。

所以，如果评审问为什么没用机器学习，回答是：*我们评估过了；这个挑战的瓶颈不是在视频中识别运动，而是获取并对齐正确的数据，并把它们呈现在人面前；AI 在这里的价值在于用作用于裁切图的小网络对候选进行筛选，这正是 ALeRCE broker 所做的，我们把它作为后续方向提出。* 这个回答比硬塞进一个没有贡献的模型要有力。

## 9. 评审团：如何评判，瞄准什么

漏斗是这样的：本地赛区的评审团选出全球提名；然后 NASA 和合作机构的专家选出决赛入围者；最后一个执行委员会选出十个全球获奖者。

也就是说：**第一道筛选是本地评审团**，每个团队时间很少，也不读代码。之后才是真正懂天文的人。项目必须在两种场合都行得通：两分钟内打动人，并经得起专家的审视。

在十个全球奖项中，有两个天然适合这个项目：**最佳数据使用**，字面上就是让空间数据可被获取；以及**最佳科学使用**。如果下功夫，还能白拿第三个：**最佳叙事使用**，因为冥王星的故事和闪烁比较器就摆在那里等着拿。瞄准两到三个，而不是十个。

## 10. 两分钟路演

在圣地亚哥的赛事中，公布的格式是两分钟加两个问题。两分钟比看起来短得多，要大声、计时地排练三次。

结构如下，顺序不可协商，因为**演示要放在讲解之前**：如果被打断，至少他们已经看到了工具。

**二十秒的开场。** 1930 年，Clyde Tombaugh 通过比较同一片天区的两张照片，发现一个点移动了，从而发现了冥王星。今天 SPHEREx 每六个月以 102 种红外颜色拍摄整个天空，而没有人这样去看它。

**五十秒的现场演示**，占一半时间，也是被评判的部分。输入“WISE 0855”——输入名称而不是坐标，以证明它适合任何人。点击播放并显示第一张与最后一张图像之差：褐矮星在移动——一对红蓝，很细微，并诚实地说明单次曝光里它看起来很暗。再展示 eps Ind B，那里的运动更清楚。拖动波段选择器：同一区域在另一个波长下的样子。
打开 Gaia 叠加层（WISE 0855 不在 Gaia 中：那里的叠加层是 CatWISE2020；在 Barnard 或 eps Ind B 上用 Gaia）：标记落在源上，*这样我们就知道它是正确的*。
复制 URL：这是可分享、可嵌入的。

**二十五秒讲为什么重要。** 已知的大多数褐矮星和彗星是志愿者通过看闪烁找到的。这个社区存在，而今天还没有办法查看 SPHEREx。被引用最多的 Planet Nine 候选者来自比较两次在时间上分开的红外巡天：同一种技术。

**以及二十五秒讲我们构建了什么、接下来是什么。**

路演的三条规则。永远不要对着冷查询做现场演示：五个天区都要预热。不要说“可以”：展示现有的东西。以及**不要承诺发现了任何东西**：有天文学家在场的评审团会立刻惩罚这一点。

关于 Planet Nine，诚实的表述是：截至 2026 年 11 月，**尚未找到**。被引用最多的候选者来自将相隔二十三年的红外巡天 IRAS 和 AKARI 交叉比对，而作者本人强调他们没有发现任何确定的东西。但有一句话是真实的、可验证的，也比任何承诺都是更好的开场：**找到那个候选者的技术正是这个挑战的技术，而 SPHEREx 每六个月就用 102 个波段做一次，且没有人用肉眼检查过。**

## 11. 令人尴尬的问题

四个，附带回答。

**IRSA 的数据浏览器不是已经在做这个了吗？** 对这类受众而言不是。浏览器是给天文学家用的档案库：你得知道请求哪个集合、多扩展 FITS 是什么，以及图像怎么拉伸。我们解析名称、归并历元、归一化，并交付闪烁。这是档案库和查看器的区别，也正是让 WiseView 相对于 WISE 档案库变得有用的那个区别。

**我怎么知道这张图像确实来自那个坐标？** 通过 Gaia 叠加层。并且在屏幕上显示出来。

**如果我输入一个没有数据的坐标会怎样？** 有人输入一个，然后显示空状态，其中说明有多少个历元，并建议一个附近的天区。这个必须解决：评审团会随机输入坐标，而空白屏幕是严重的失败。

**光谱有多正确？** 它们是示意性的，是扣除了黄道光的孔径测光，我们在界面本身就这样说明。用于科学研究时有 IRSA 的分光光度工具。永远不要把它们作为科学品质展示：在这里，诚实加的分远多于它减的分。

## 12. 交付中的强制项

三件不是走过场的事。

**今年，每份提交都必须附带对人工智能使用方式的描述。** 写得好，它就是方法的证据：向助手要求了什么、如何控制结果、没有用它们做什么——特别是，没有任何科学数据由模型生成或补全——以及为什么经过论证放弃了用于检测的视觉模型。写得不好，就是白白浪费了一次机会。

**SPHEREx 数据的署名**，逐字照录，放在工具的页脚和 README 中。这是在 NASA 评审面前白拿的严谨分，只需三十秒。

还有**在赛事 Wi-Fi 之外测试过的链接**：视频、已部署的应用和仓库，用手机的移动数据打开。只在局域网里能用的链接就是坏链接。

## 13. 到场时脑子里要带什么

五件事。

一：题面中的八条建议就是评分标准，七条很便宜，要按价值顺序全部完成。

二：第八小时的里程碑是屏幕上的一段小视频，无论多丑。其他一切都服从于它。

三：三个停靠点——六小时冻结、四小时录好演示、两小时已提交——不可协商，因为获胜的项目是完整交付的那个。

四：验证产物，而不是报告。对智能体适用，对人也适用。

五：项目的角度一句话就能说完。**一个查看器，任何人输入一个坐标，就能同时看到两个轴：这片天区如何随时间变化，以及它在 102 个波长上各自是什么样子，并附有对所指对象即时生成的光谱。** 这是对题面的字面解读，是它最苛刻的两个要点，也是如今没有任何公共工具做到的事。
