# 在平台上提交

**一个好项目一无所获的头号原因,是提交得晚或不完整。**
这个 skill 的存在就是为了避免这种情况。

**规则:** 提交在 **T − 2 h** 上传,而不是在 T。之后仍可继续编辑,但已经
算提交了。

**N 在活动的第 1 小时就打开表单**,而不是第 22 小时,以便看它真正要求什么。
这里的内容是我们所知道的;以平台为准。

---

## 提交要求什么(我们所知道的)

- 项目名称和简短摘要。
- 项目描述:它做什么、怎么做的、使用了什么数据。
- **关于项目中如何使用 AI 的说明。今年是强制的。**
- 演示链接(视频或已部署的应用)。
- 代码仓库的链接。
- 所使用的资源和数据,附来源。

通过 spaceappschallenge.org 上团队的项目页面提交,按当地活动的截止
时间:**周日11月15日,11:00**(JP 于11月14日确认)。在 09:00(T − 2 h)提交。

## 模板

### 简短摘要

> *(一两句话。评审团首先读到的,有时也是唯一读的。)*
>
> `<Nombre>` 是一个公开的网页工具,以 SPHEREx 观测到的样子展示天空的任意一块区域随时间的变化,
> 就像一段小视频,让任何人都能检测移动或亮度变化的天体。它增加了光谱轴:该任务的
> 102 个红外波段
> *(只有当 `/api/spectrum` 进入演示时,才加上「并即时生成光谱」)*。

### 描述

四个部分,按此顺序:

1. **问题。** 为什么需要:SPHEREx 每六个月绘制整个天空,共 102
   个波段,而没有人在用它寻找移动的东西。闪烁技术发现了
   冥王星,并且靠志愿者继续发现褐矮星和彗星。
2. **我们构建了什么。** 查看器、控件、叠加层、可分享的 URL。**已有的**,
   而不是计划中的。
3. **我们如何构建。** 所使用的真实数据(发布版本、集合、IRSA 服务)、
   技术栈,以及不得不解决的问题——**尤其是线性可变滤光片的问题**,
   它证明我们理解了这台仪器,而不只是下载了图像。
4. **接下来。** 诚实地说:我们没来得及做什么,以及原因。

### AI 使用声明

这不是走过场。写得好,它就是方法的证据。写得不好(「我们用 ChatGPT 编程」)
就浪费了一个机会。

> **我们在本项目中如何使用人工智能**
>
> 我们使用基于语言模型的编程助手(Claude Code 和 Antigravity)作为活动 24 小时期间的
> 开发工具,并采用明确的方法:
>
> - **我们让它们做什么:** 编写与 IRSA 档案对接的集成代码、界面组件、
>   测试和文档,依据的是团队在开始时确定、并已在仓库中纳入版本管理的 API 契约
>   和约定(`AGENTS.md`)。
> - **我们如何控制结果:** 每一项改动在整合之前都经过人工审查。
>   我们遵循验证产物而不是报告的规则:没有任何功能仅因助手说完成了就被
>   视为完成,而是在打开它并对照真实数据
>   和外部星表核实之后。
> - **我们没有做什么:** 我们没有使用模型来生成、编造或补全科学数据。
>   工具所显示的所有图像、波长和元数据都来自 SPHEREx 任务
>   通过 IRSA 发布的文件。
> - **为什么我们没有使用视觉或视频模型来做检测:** 我们评估过,并
>   有理有据地放弃了。挑战要求的是供人来检测的查看器;真正的瓶颈
>   是数据的获取和对齐。我们在仓库中记录了
>   模型在哪里确实有用——用小型网络对裁切图做候选体筛选,类似
>   ALeRCE broker——作为后续工作。
>
> *(按实际情况调整。如果用了别的东西,就说明。如果 Spherix 在生产环境中使用 LLM,请在此声明模型以及它接收哪些数据。)*
